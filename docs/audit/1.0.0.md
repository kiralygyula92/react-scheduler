# Pre-publish audit — 1.0.0

The audit docs pack `09` §10 requires before `1.0.0`: what the package depends on, how it renders,
how fast it is, what is missing, what is broken, whether its API is consistent, and which gates it
passes. Every number here comes from a command run on the `m7-audit` branch; the command is named
next to it so the number can be reproduced.

- **Package:** `@react-schedulerkit/react-scheduler`. Audited at `0.0.0` on `m7-audit`; versioned as
  `1.0.0` (`changeset version`) in the release preparation, which added the security review in §8.
- **Measured on:** Windows 11, Node 24.21.0, pnpm 10.34.5, Playwright 1.63 (Chromium, Firefox,
  WebKit).
- **Verdict:** no open blocker. Three findings are recorded and accepted (§5); one was a real bug and
  is fixed (§2).

### Memory

`test/browser/perf/memory.perf.test.tsx`: 20 mount/unmount cycles of each view with forced garbage
collection. Heap growth **3.3 %** (list) and **1.3 %** (timeline) against the Dossier's 5 %; DOM
nodes (75), event listeners (26) and documents (2) identical before and after. No leak.

### Re-render counts

The main interactions are pinned by tests rather than profiled by hand: a single item change
re-renders only that item's card, in both views; a clock tick re-renders no card, hour label or hour
line; a pin refresh costs 0.1 ms per frame. Together they are the render-count test the Dossier asks
for (`09` §3).

## 6. API review

- **Naming (`09` §4.2)** — checked over all 95 props of `Scheduler`: all seven state pairs follow
  `defaultX` / `x` + `onXChange` (`date`, `view`, `headerExpanded`, `openItemId`, `openOverflowId`,
  `overflowSort`, `overflowPage`); the twelve render props are `renderX`; feature flags are
  `enableX`. The five booleans that are not `enableX` are state or modes, not features (`loading`,
  `headerExpanded`, `defaultHeaderExpanded`, `keepInactiveViewMounted`, `unstyled`). Slots,
  `slotProps`, `handlers.onX`, `localization`, `classNames`/`styles`, the `rs-` class prefix, the
  `--rs-` variables and the `data-rs-*` attributes follow the table.
- **No `any` in public types** — a search of `src/` finds the word only in comments; `publint` and
  `attw` report no problem (`lint:pkg`).
- **No dead parameters** — `noUnusedParameters` and `noUnusedLocals` are on for the package, and
  `knip` reports no unused file, export or dependency.
- **Reference** — every exported symbol has a page, and every member a description in seven
  languages (conformance C6); the Playground covers every prop (C7).

## 8. Security review

Run in the 1.0.0 release preparation (2026-09-25), over the package, the site, the scripts and the
workflows. Three findings were fixed; two are recorded — one for the first publish, one for the Vercel setup.

**The package** has no sink an attacker's data could reach: a search of `packages/react-scheduler/src`
for `dangerouslySetInnerHTML`, `innerHTML`, `insertAdjacentHTML`, `document.write`, `eval`,
`new Function`, `fetch`, `XMLHttpRequest`, `postMessage`, `window.open`, web storage and
`location` assignments finds nothing outside tests. Item titles, labels and every localized string
reach the DOM as React text. It has no runtime dependency, so no transitive one either.

**The site** renders through React too. The one `dangerouslySetInnerHTML` is the theme bootstrap in
`root.tsx`, a constant from `src/shell/theme-bootstrap.ts` with no input. The Playground reads its
configuration from `?p=`: unreadable links fall back to the defaults, only props that have a control
are applied, values are parsed by the control's kind, and the generated item count is clamped to
0–500, so a crafted link can neither inject markup nor ask the page for a million items.

**Dependencies:** `pnpm audit` — no known vulnerabilities. **Secrets:** no `.env`, key or token file
is tracked (`.npmrc` holds only the `tslib` hoist pattern), and `git grep` for npm, GitHub, AWS and
private-key patterns finds nothing.

| Finding                                                                                                                                                                                                        | Severity              | Decision                                                                                                                                                                                                                       |
| -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `apps/docs/scripts/serve.ts` (the local production server the e2e suite and Lighthouse use) resolved `%2e%2e` paths outside `build/client`, listened on every interface, and crashed on a malformed `%` escape | Medium                | **Fixed**: every path is resolved and must stay inside `build/client` (404 otherwise), the server listens only on the addresses `localhost` resolves to, and a bad escape answers 400. Checked by hand against each case       |
| GitHub Actions were referenced by moving tags (`@v4`), and the release job installed `npm@latest` — a re-pointed tag or a bad npm release would run with `id-token: write`                                     | Medium                | **Fixed**: every `uses:` names a full commit SHA with its version beside it, and npm is pinned to `11.19.0` (GAPS G8's SHA item)                                                                                               |
| Translations turn `<link to>` and `<ext href>` into links straight from the locale files, and nothing checked the targets — a `javascript:` or plain-http URL in a translation would have reached the page     | Low                   | **Fixed**: `i18n:check` requires every `<link to>` to be a site path and every `<ext href>` an `https:` URL                                                                                                                    |
| The GitHub repository is private, while the package declares `provenance: true` and links to it for its source, issues and vulnerability reports                                                               | High, for the release | **Recorded** (GAPS G15): visibility is the owner's decision. `docs/release/npm.md` §0.3 makes it the first thing to settle before publishing                                                                                   |
| The site sends no security headers beyond Vercel's own; `vercel.json` is the pack's                                                                                                                            | Low                   | **Recorded**: static site, no forms, sign-in or user data, so nothing depends on them. `docs/release/vercel.md` §6 gives scoped `nosniff` and `Referrer-Policy` rules to add, and what a CSP would need, once a preview exists |

The release path was checked as well. `release.yml` keeps its write permissions and `id-token: write`
because Changesets and Trusted Publishing need them, runs only while `RELEASE_ENABLED` is `true`, and
publishes nothing before the tarball passes the zero-reference scan and `pnpm release:sandbox`. The
sandbox now also type-checks the tarball with TypeScript 5.0.4, 5.9.3, 6.0.3 and 7.0.2, so the
Requirements page's TypeScript range is verified at every release rather than stated once.
